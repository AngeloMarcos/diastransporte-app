# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Dias Transporte" — a transfer/booking site for São Luís ↔ Lençóis Maranhenses (MA) routes, built with **TanStack Start** (SSR React). The project currently runs on **Lovable Cloud (Supabase)** and is **mid-migration to a self-hosted VPS** with its own Postgres and custom auth — both backends are live in the codebase behind a single flag (see "Two backends, one data layer" below). While on Lovable, pushing to `origin/main` syncs the commit into the Lovable editor and the live app at `wander-book-craft.lovable.app` — there is no separate deploy step for that path. See `.claude/skills/vps-deploy/SKILL.md` and `.claude/skills/vps-db/SKILL.md` for the VPS migration's operational status (as of writing: schema, Docker/CI, and app code for the VPS path are all done; it's blocked purely on SSH key authorization on the server).

## Commands

```sh
npm install          # node_modules is not committed
npm run dev           # vite dev server
npm run build          # production build (vite build; nitro/cloudflare target)
npm run preview          # preview a production build
npm run lint          # eslint (flat config, eslint.config.js)
npm run format          # prettier --write .
npm run test          # vitest run — unit tests for pure logic only, see below
npm run test:watch      # vitest in watch mode
npx tsc --noEmit -p tsconfig.json   # typecheck (no npm script defined for this)
```

**Tests**: Vitest, config in `vitest.config.ts` (deliberately separate from `vite.config.ts` — the latter loads `@lovable.dev/vite-tanstack-config`'s TanStack Start/nitro/Cloudflare plugin stack, which has no business running inside a test runner and might not even work there). Only covers pure logic with no live backend — validation helpers (`senha.ts`, `auth-erros.ts`), pricing (`data/rotas.ts`), the WhatsApp message builders, the `status.ts` counters, and the localStorage-backed cart functions in `carrinho.ts` (not the `useCarrinho()` hook itself). There is intentionally no e2e suite: this project has a single Supabase project (no separate staging/test instance), so a Playwright-style test that actually completes a booking would write real rows into the production `agendamentos` table. Don't add e2e/integration tests against the live Supabase project without addressing that first (a second project, or pointing at the VPS Postgres once it's live). Gotcha if you touch `formatBRL`'s tests: `Number.prototype.toLocaleString("pt-BR", { style: "currency" })` separates "R$" from the amount with U+00A0 (non-breaking space), not a plain space — comparing against a hand-typed `"R$ 650"` literal will silently fail on that character alone.

Before pushing, always run typecheck + lint + build; `tsconfig.json` is strict (`noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `exactOptionalPropertyTypes`, `strict`), so code that looks fine at a glance (e.g. `record.someKey`, or trusting an indexed array access) routinely fails typecheck. Index into `Record<string, T>` with bracket notation, and treat indexed/array access as possibly `undefined`.

**Windows CRLF gotcha:** files checked out on this machine often have CRLF line endings, which trips `prettier/prettier` across the *entire* file (not just edited lines) the first time `eslint` runs on them, even for lines you didn't touch. If `eslint` reports a wall of `Delete '␍'` errors, run `npx eslint --fix <file>` — this is expected and not a sign your edit broke something.

## Architecture

**Routing** is TanStack Start's file-based router — see `src/routes/README.md` for the naming rules (`$param`, `{-$optional}`, `$` splat, `_layout`, `__root.tsx`). `src/routeTree.gen.ts` is auto-generated by the router plugin on dev/build; never hand-edit it. `_authenticated/route.tsx` is a pathless layout route whose `beforeLoad` redirects to `/auth` when there's no Supabase session — `admin.tsx` and `minhas-viagens.tsx` live under it.

### Two backends, one data layer

The single most important fact about this codebase: **every screen calls `src/lib/dados.ts`, never Supabase or the VPS Postgres directly.** Each exported function there (`listarRotasAdmin`, `criarReservas`, `enviarImagem`, `perfilContato`, ...) branches on `MODO_VPS` (`src/lib/vps/config.ts`, reading `VITE_AUTH_MODE === "vps"`) and calls one of two implementations that are kept schema-compatible on purpose:

- **Lovable Cloud (Supabase)** — today's live backend. `supabase` (`src/integrations/supabase/client.ts`, anon key, RLS-scoped) is used directly from these branches; `client.server.ts` (service-role, bypasses RLS) is only loaded inside server handlers via dynamic `await import(...)`, never top-level, since route files and `*.functions.ts` ship to the client bundle. `src/lib/*.functions.ts` (`rotas.functions.ts`, `conteudo.functions.ts`) are `createServerFn` handlers that build their own throwaway anon client from `process.env` for public SSR data loading. Files marked `// This file is automatically generated.` / `// auto-generated by Lovable.` (the Supabase client/middleware files, `src/integrations/lovable/index.ts`) are managed by Lovable's integration — edit the Supabase schema/config instead of hand-patching these.
- **Self-hosted VPS (own Postgres)** — code-complete, not yet live (blocked on SSH access to the server, see `.claude/skills/vps-deploy/SKILL.md`). `src/lib/vps/*.server.ts` talks to Postgres directly via the `postgres` npm package (`db.server.ts`), with its own bcrypt+cookie session auth (`auth.server.ts`) instead of Supabase Auth/RLS — authorization is enforced in the server functions themselves (`exigirUsuario`/`exigirAdmin`), not by the database. `src/lib/vps/dados.functions.ts` mirrors every operation `dados.ts` needs as a `createServerFn`. `db/migrations/*.sql` mirrors `supabase/migrations/*.sql`'s schema (plus `usuarios`/`sessoes` tables and a `profiles` view for compatibility) minus RLS/PostgREST-specific bits; apply with `db/migrate.mjs` (idempotent, tracks applied files in `public.schema_migrations`). `db/seed.sql` has real data exported from Supabase; `db/migrar-imagens.mjs` re-downloads route photos from the live Lovable app onto VPS disk and rewrites the DB rows to `/api/uploads/...`. Deploy is Docker Compose (`docker-compose.yml`, `Dockerfile` — nitro preset `node_server` instead of Lovable's `cloudflare`) via GitHub Actions SSH (`.github/workflows/deploy.yml`, not yet runnable — needs the `SSH_HOST`/`SSH_USER`/`SSH_KEY` repo secrets and VPS access first).

**Implication for new features or integrations**: add the operation to `dados.ts` with both branches (even if the VPS branch is a stub for now), not just to whichever backend you're testing against — the two are meant to stay interchangeable so the eventual cutover is a one-line env var flip, and any future third-party integration should sit behind this same seam rather than importing `supabase` or `sql()` from route/component code directly.

**Auth**: `useAuth()` (`src/hooks/useAuth.tsx`) exposes `{ user, isAdmin, carregando }` regardless of backend. On Supabase, `isAdmin` resolves via a `user_roles` row (`role = 'admin'`); `src/integrations/lovable/index.ts` wraps Lovable's OAuth (Google et al.) and hands tokens to the Supabase client via `setSession`. In `MODO_VPS`, there's no OAuth — `isAdmin` is a plain `usuarios.admin` boolean, and the "session" is an opaque token in an `HttpOnly` cookie (`dias_sessao`), hashed (SHA-256) before being stored in `public.sessoes`; `_authenticated/route.tsx`'s `beforeLoad` checks whichever backend is active before allowing `/admin` and `/minhas-viagens`.

**Cart & checkout** (`src/lib/carrinho.ts` + `src/lib/reserva.ts`): the "select routes → create account → request transport" flow is cart-based, not single-booking. `carrinho.ts` is a `localStorage`-backed cart (client-only, `useCarrinho()` hook) that survives navigation and the auth redirect untouched — items carry `rotaId` but never a client-computed price. `reserva.ts` only stores *where to redirect back to* after `/auth` (`sessionStorage`), since the cart itself doesn't need restoring. Checkout (`carrinho.tsx`) calls `criarReservas()` in `dados.ts`, which fans out to one insert per cart item; **the price is never trusted from the client** — both schemas compute `agendamentos.valor` server-side via a `BEFORE INSERT/UPDATE` trigger (`agendamentos_calcular_valor`) keyed off `rota_id` + `carro` + `periodo`, so `NovaReserva` (`dados-tipos.ts`) deliberately has no `valor` field.

**Data model** (source of truth: `supabase/migrations/*.sql` on Lovable, `db/migrations/*.sql` on the VPS — keep both in sync when changing schema): `rotas` (routes/pricing, public when `ativo`), `agendamentos` (bookings; `rota_id` required, price server-computed, `user_id` nullable with `ON DELETE SET NULL` so history survives account deletion), `conteudo_site` (CMS-style key/value blocks via `mapearConteudo`/`texto()` in `src/lib/conteudo.ts`, keyed by a `chave` like `home_hero`), and either `profiles`+`user_roles` (Supabase) or `usuarios`+`sessoes` (VPS, with a `profiles` view for read compatibility). Admin CRUD for all of these lives in `src/routes/_authenticated/admin.tsx`, entirely through `dados.ts`.

**Uploads**: route photos and content images. On Supabase, `enviarImagem()` uploads to the `rotas` storage bucket and returns a long-lived signed URL. In `MODO_VPS`, it POSTs to `/api/uploads` (`src/routes/api/uploads.ts`), which requires an authenticated admin, validates MIME/size, and writes to `UPLOADS_DIR` on disk (`src/lib/vps/uploads.server.ts`); `src/routes/api/uploads.$arquivo.ts` serves them back (Nginx/Caddy would normally front this in production).

**Styling**: Tailwind v4 (CSS-first config in `src/styles.css`, no `tailwind.config.js`) with a fixed dark theme (oklch tokens) — there is no light/dark toggle, don't add theme-conditional styling expecting one. UI primitives are shadcn/radix components under `src/components/ui/` (generated, edit them like normal source, not a locked vendor dir).

**Error handling**: `src/server.ts` is the SSR entry (Cloudflare Worker on Lovable, plain Node on the VPS via the `node_server` nitro preset); it and `src/start.ts` both wrap SSR failures to render `src/lib/error-page.ts`'s HTML instead of leaking a raw 500/h3 error, since h3 sometimes swallows in-handler throws into a JSON `{"unhandled":true}` body that a plain try/catch won't see (`normalizeCatastrophicSsrResponse` detects that shape specifically).

## External integration points (for future third-party work)

Nothing today talks to an outside system through a formal API — everything is either browser→server-function (internal) or a raw link the user's own device opens:

- **WhatsApp**: `src/lib/whatsapp.ts` only builds `wa.me/<number>?text=...` deep links (`whatsappLink`, `mensagemReserva`, `mensagemCarrinho`) — there's no WhatsApp Business API, no webhook, no delivery/read confirmation. A booking "completing" today just opens a pre-filled chat; nothing is pushed anywhere automatically.
- **Email/SMS**: not configured on either backend. The VPS migration notes flag this as an open gap even for the migration itself (signup confirmation, password reset need a transactional provider — SMTP/Resend/SES — nobody has set one up yet).
- **Payments**: none. Bookings are unpaid reservation requests confirmed manually over WhatsApp.
- **Inbound API surface**: none exposed for external systems to call in. All `createServerFn`s in `*.functions.ts` and `src/lib/vps/*.functions.ts` are same-origin RPC endpoints for this app's own client, not a documented/versioned public API; `src/routes/api/` today only holds the upload endpoints. A real integration (channel manager, accounting/ERP, payment webhook receiver) would need new routes under `src/routes/api/` with their own auth (e.g. a shared secret checked with `comparaSegura()` in `vps/auth.server.ts`, which already exists for exactly this: constant-time token comparison for webhook-style checks).
- Whatever gets built should go through `dados.ts` (see above) if it reads/writes `rotas`/`agendamentos`/`conteudo_site`, so it keeps working across both backends during the migration window instead of hard-coding to whichever one is live today.
