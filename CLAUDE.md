# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Dias Transporte" — a transfer/booking site for São Luís ↔ Lençóis Maranhenses (MA) routes, built with **TanStack Start** (SSR React) and **Supabase**. The project is connected to **Lovable** (see `AGENTS.md`): pushing to `origin/main` syncs the commit into the Lovable editor and the live app at `wander-book-craft.lovable.app`. There is no separate deploy step — `git push origin main` *is* the deploy.

## Commands

```sh
npm install          # node_modules is not committed
npm run dev           # vite dev server
npm run build          # production build (vite build; nitro/cloudflare target)
npm run preview          # preview a production build
npm run lint          # eslint (flat config, eslint.config.js)
npm run format          # prettier --write .
npx tsc --noEmit -p tsconfig.json   # typecheck (no npm script defined for this)
```

There is no test suite in this repo (no test runner configured, no `*.test.*` files) — do not assume one exists.

Before pushing, always run typecheck + lint + build; `tsconfig.json` is strict (`noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `exactOptionalPropertyTypes`, `strict`), so code that looks fine at a glance (e.g. `record.someKey`, or trusting an indexed array access) routinely fails typecheck. Index into `Record<string, T>` with bracket notation, and treat indexed/array access as possibly `undefined`.

**Windows CRLF gotcha:** files checked out on this machine often have CRLF line endings, which trips `prettier/prettier` across the *entire* file (not just edited lines) the first time `eslint` runs on them, even for lines you didn't touch. If `eslint` reports a wall of `Delete '␍'` errors, run `npx eslint --fix <file>` — this is expected and not a sign your edit broke something.

## Architecture

**Routing** is TanStack Start's file-based router — see `src/routes/README.md` for the naming rules (`$param`, `{-$optional}`, `$` splat, `_layout`, `__root.tsx`). `src/routeTree.gen.ts` is auto-generated by the router plugin on dev/build; never hand-edit it. `_authenticated/route.tsx` is a pathless layout route whose `beforeLoad` redirects to `/auth` when there's no Supabase session — `admin.tsx` and `minhas-viagens.tsx` live under it.

**Supabase clients — three, not interchangeable:**
- `src/integrations/supabase/client.ts` — browser/SSR client, anon key, RLS-scoped to the signed-in user. Import as `supabase` almost everywhere.
- `src/integrations/supabase/client.server.ts` — service-role client that **bypasses RLS**. Only load it inside server handlers (`await import(...)`, not a top-level import) since route files and `*.functions.ts` ship to the client bundle.
- `src/lib/*.functions.ts` (e.g. `rotas.functions.ts`, `conteudo.functions.ts`) — `createServerFn` handlers that build their *own* throwaway anon Supabase client from `process.env` for SSR data loading (public data only), independent of the two clients above.

Files marked `// This file is automatically generated. Do not edit it directly.` or `// This file is auto-generated by Lovable.` (the three Supabase client/middleware files, `src/integrations/lovable/index.ts`) are managed by Lovable's Supabase integration — edit the Supabase schema/config instead of hand-patching these.

**Auth**: `useAuth()` (`src/hooks/useAuth.tsx`) exposes `{ user, isAdmin, carregando }`, resolving `isAdmin` via a `user_roles` row (`role = 'admin'`) rather than a claim. `src/integrations/lovable/index.ts` wraps Lovable's OAuth (Google et al.) and hands the resulting tokens to the normal Supabase client via `setSession`, so downstream code only ever deals with `supabase.auth`.

**Booking draft persistence** (`src/lib/reserva.ts`): the "select a route → create account → request transport" flow spans an unauthenticated → authenticated boundary. Booking form state gets saved to `sessionStorage` before redirecting to `/auth`, and a post-login redirect path is stashed alongside it; `auth.tsx` reads both after a successful sign-in/sign-up and sends the user back to the route detail page with their in-progress booking restored. Extend this pattern rather than adding a second ad-hoc draft mechanism if another multi-step flow needs to survive a login redirect.

**Data model** (see `supabase/migrations/*.sql` for the source of truth): `rotas` (routes/pricing, public when `ativo`), `agendamentos` (bookings, RLS: owner or admin), `conteudo_site` (CMS-style key/value blocks rendered via `mapearConteudo`/`texto()` in `src/lib/conteudo.ts`, keyed by a `chave` like `home_hero`), `profiles` + `user_roles`. Admin CRUD for all of these lives in `src/routes/_authenticated/admin.tsx`.

**Styling**: Tailwind v4 (CSS-first config in `src/styles.css`, no `tailwind.config.js`) with a fixed dark theme (oklch tokens) — there is no light/dark toggle, don't add theme-conditional styling expecting one. UI primitives are shadcn/radix components under `src/components/ui/` (generated, edit them like normal source, not a locked vendor dir).

**Error handling**: `src/server.ts` is the Cloudflare Worker entry; it and `src/start.ts` both wrap SSR failures to render `src/lib/error-page.ts`'s HTML instead of leaking a raw 500/h3 error, since h3 sometimes swallows in-handler throws into a JSON `{"unhandled":true}` body that a plain try/catch won't see (`normalizeCatastrophicSsrResponse` detects that shape specifically).
